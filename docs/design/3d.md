# Backbone 3D design

Status: proposal. A working prototype exists on the local branch `demo-3d` (commit `5e6ea3d`). This document describes where the 3D mode should go and in which order, so that a separate agent can pick it up.

## Idea

The player gets a first-person view of their company. They start in the basement, sit at a desk and use the game on a computer or laptop. When something needs hands-on work they stand up, open the door, pick a destination on a map and travel there. In the datacenter they walk between racks, look at the real hardware and install, remove or change devices in the rack with their own hands.

The 2D desktop stays the game. The 3D world is a way to be somewhere, not a second game. Everything the player can do in 3D calls the same actions as the 2D UI.

## Pillars

- **The 2D desktop is the source of truth.** The laptop and the computer show the real game. Nothing exists only in 3D.
- **3D is a view over the simulation.** `src/sim` never imports three.js or anything 3D. The 3D layer reads state and calls actions through the store's `act`, like any app.
- **Presence matters.** Some work needs the player to stand at the rack, and travel costs game time. This is what makes the world worth walking through.
- **Low poly, drawn from the game's own art.** Props are boxes and primitives. Racks and device fronts are textures made from the existing SVG art, so 3D and the Locations app always agree.
- **Static site only.** The 3D mode ships as part of the same static build.

## Non-goals

- Free-roam outdoors, multiplayer, physics, or a model and animation pipeline.
- Mobile support. The mobile gate screen stays.
- Rebuilding fine work (cabling, port configuration, consoles) in 3D. Those stay in the 2D UI.

## The experience

**Basement.** A small room with a desk, a computer, a pick-up laptop, a rack against the back wall and a door. The computer opens the game as a fullscreen overlay. The laptop can be taken and opened with Tab anywhere.

**Door and map.** The door opens a 2D map, built on the existing world map. The player picks a location, a travel time passes, and the scene for that location is built from the save. Only the current location exists in the scene.

**Datacenter.** Rows of racks that match the racks and devices in the save. The player aims at a slot or a device and presses E for the actions that make sense there.

**Phone (later).** A phone that pages the player when something breaks and they are on call. Out of scope until the on-call model exists in the simulation.

## Where each action lives

| Action | Where |
| --- | --- |
| Buy, plan, configure, customer and company work | 2D desktop on the laptop or computer |
| Install, remove or move a device at a unit | 3D, at the rack, through a small menu on the aimed slot |
| Cabling, port settings, consoles, power details | 2D overlay: the live `RackFront` opened for the focused rack |
| Choosing a location | Map opened from the door |
| Inspecting status | Both: LEDs and labels in 3D, details in the 2D UI |

## Architecture

**Layers.**

- `src/sim/` holds all rules, including travel and presence. No 3D code.
- `src/world3d/` (new) is the 3D view. It reads state and calls `act`.
- `src/ui/` is unchanged and is reused for every overlay.

**World as data.** A location's rooms, doors, rack slots and prop positions are described by plain TypeScript data. A generic builder turns that data into meshes and collision boxes. Layout and collision logic are pure functions and get seeded tests: rack N lands in slot N, every door is passable, nothing overlaps.

**Modules.** The prototype is two files; the real version splits into:

- `player`: movement, look, bob, footsteps.
- `world`: builds a location from data and state.
- `racks`: rack and device meshes, texture cache, slot picking.
- `interact`: aim, prompt, use, context menus.
- `overlays`: laptop frame, map, pause menu.

**State flow.** Each frame reads state from the store. When a rack's contents change, only that rack's texture is regenerated. Player actions call `act` and the scene updates from the new state.

## Rack art pipeline

The prototype renders the game's `RackFront` component to an SVG string with `react-dom/server`, loads it through an image into a canvas and uses it as the texture of a plane in front of a box. One rack unit is drawn 18 px tall and mapped to 44.5 mm, so a 24 U rack is about 1.1 m tall and a 42 U rack about 2 m.

Open items:

- The art is drawn about 14 units wide per unit height, wider than a real 19 inch rack. Either accept the stretch, or add a narrower art variant for 3D.
- Every SVG currently embeds the full shell and locations stylesheets (about 119 KB). Reduce this to the variables and rack rules the art needs.
- Fonts used in the art are not available inside an SVG loaded as an image. Pick fallbacks or inline the glyphs that matter.
- LED blinking in the art does not run inside an image. Blinking is done by the 3D layer, for example by animating a small overlay or swapping textures near the player.

## Slot picking

The rack face is one plane at a known scale. A ray hit gives a UV coordinate, which converts to a pixel row and then to a rack unit. The unit maps to the existing slot and device in the save. The same numbers drive the highlight of the aimed unit.

The slot menu offers only actions the sim allows: remove, install from inventory, move. Each calls the existing hardware action. The sim stays the authority on whether the action works.

## Simulation changes required

Each item is a feature of its own with seeded tests, designed before any 3D work depends on it.

- **Player location.** Where the player is (basement, a datacenter, in transit) and when they arrive.
- **Travel.** Trips take game time. Rules decide which actions work remotely and which need presence.
- **Presence rules.** Hardware actions check that the player is at the location. Old saves load as being at the basement, so every new state field gets a default in `newGame` and `deserialize` fills it.
- **Carrying.** A device removed from a rack goes to the player's hands or inventory, and installing takes from there.
- **On call (later).** An on-call state, a paging queue, acknowledgement deadlines and escalation.

All text the simulation produces goes through i18n keys.

## Performance plan

Estimates, to be measured before any work depends on them:

- One location at a time keeps the scene size bounded.
- Each 42 U rack texture at double resolution is about 4 MB of GPU memory, so 16 distinct racks are about 70 MB. A 100-rack location needs a cheaper representation for racks far from the player: a flat color with LED dots, and the full art only for racks within a few metres.
- Rendering the SVG and decoding the image costs tens of milliseconds, so regeneration is debounced and limited to changed racks.
- Instanced meshes for repeated props keep draw calls low.
- Rendering pauses while a fullscreen overlay is open.

Measure first: frame time and GPU memory in a 16-rack and a 100-rack location on a mid-range laptop, before choosing the level-of-detail scheme.

## Packaging

The 3D mode ships in the browser build first. A desktop build wrapped with Tauri is a packaging step on the same code, adds OS notifications for the phone and file-based saves, and needs no separate features. The game design document currently lists "no Steam" and "browser game"; if a desktop release becomes a goal, that line is updated in the same change.

## Changes to existing documents

- `gdd.md` pillar "You sit at a desk" gains the walkable world, and the Locations row of the app table notes that the floor and rack views move into the 3D world.
- `gdd.md` platform and scope is updated if a desktop build is adopted.
- `economy.md` gets travel time and any travel cost.

## Phases

Each phase ends with something playable and does not depend on a later one.

1. **Sim foundations.** Player location, travel and presence rules, with seeded tests and a 2D control for travel.
2. **World from data.** The layout description, the builder, the basement and one datacenter built from a real save, collision tests.
3. **Map and door.** The map overlay, scene swap, fades and travel time.
4. **Slot picking.** UV to unit, aimed highlight, the slot menu calling existing hardware actions.
5. **Focused rack overlay.** The live `RackFront` for cabling and ports.
6. **Performance pass.** Measure, trim the embedded CSS, add the level-of-detail scheme.
7. **Phone and on call.** After the on-call model exists in the simulation.
8. **Desktop packaging.** Tauri wrapper, OS notifications, file saves.

## Open questions

- Does presence become a hard requirement for hardware work, or an optional bonus such as faster repairs? The first is more immersive, the second is gentler for players who prefer the desktop.
- Is travel time free, costed, or a decision with consequences such as missing a page?
- Should the 3D world be optional, with the 2D Locations app staying as an equivalent path?
- Does the laptop run the same game instance as the computer, or are they separate sessions? The prototype runs the real game in an iframe, which shares storage but not live state.
- What happens to the device in hand when the player leaves the location?

## Prototype notes

The `demo-3d` branch is a throwaway proof of feel and of the rack-art pipeline. It contains the walkable basement, a door, a corridor and one datacenter, rack textures from `RackFront`, a pick-up laptop that opens the real game in an iframe, an Esc pause menu, and walking with head bob, sprint and footsteps. It uses sample rack contents instead of the save. Its code is one large file with hard-coded coordinates and is not meant to be merged. The new modules should be written to the layout above.

Known gaps in the prototype: mouse look and the pause menu on a real pointer lock were not exercised in the test browser, and its performance has not been measured.

## Working rules for the agent building this

- Read `CLAUDE.md` first. The hard rules apply: no server, player actions only through `src/sim/90-actions`, old saves keep loading, every sim change has a seeded test, text through i18n keys, changelog bullets for player-facing changes.
- Start from `origin/main` in a worktree, not from the shared checkout.
- Commit each green piece and push to main in small steps.
- Keep the 3D layer out of `src/sim`.
