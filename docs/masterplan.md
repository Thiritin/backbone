# Backbone masterplan

This is the work plan for the next stretch of Backbone. It lists what is built and the lanes still to do, in order, with a full brief for each. Every brief is written for an implementer with no other context: it names the files, the current behaviour, the rules to build and the numbers to use. Read CLAUDE.md, docs/design/gdd.md, docs/design/economy.md and DESIGN.md before starting a lane, then read the code the brief names.

## Working rules

- The owner wants the game complete and playable and authorizes autonomous decisions. Record every rule in docs/design/gdd.md and every number in docs/design/economy.md, with its real-world anchor. Where this plan settles a choice, build it as written; where it delegates one ("pick within these bounds"), pick, build and record.
- Design preferences from past corrections: no dropdowns (segmented controls, tabs, cards, chips); card grids and sidebars like the Shop and Billing apps; right-click menus for per-object actions; UI copy is labels and values only, captions are full sentences with a verb, never leak internals or name customer types on individual customers; every real company is a pun (Dwell, Hewlett-Packet, SuperMacro, Lenovoid, Sysko, Junipurr, Goggle, Hetzna); dry humour; no em dashes anywhere.
- Player actions live in src/sim/90-actions and the UI calls them through the store's `act` (src/ui/store.ts:61). Sim-produced text goes through src/i18n/en.ts keys (and the per-topic files it imports, such as src/i18n/security.ts and src/i18n/addresses.ts); every event key has `.title` and `.text` (tests/event-keys.test.ts checks it). UI labels stay inline.
- Every sim change has a seeded test in tests/ (one suite per feature; tests/fixtures.ts has `readyGame(seed)`, `withServer(s)`, `hypervisor`, `panelServer`, `panelVm`, `basement`). Old saves must load: every new state field gets a default in `newGame` (src/sim/50-state.ts) and `deserialize` (src/sim/91-save/save.ts:27) fills it; device fields go through `deviceDefaults` (50-state.ts:154). The game is in development, so no compensation or grandfathering work.
- Hotspot files (src/sim/50-state.ts, src/sim/88-tick/tick.ts, src/sim/91-save/save.ts, src/i18n/en.ts, src/ui/apps/registry.ts, src/ui/store.ts): keep edits additive and put logic in the lane's own modules. Window sizes live in `WINDOW_SIZES` in src/ui/store.ts:23 (not exported, keyed by app name, fallback 760 by 480).
- Hand tasks (used by Lanes 2, 2b, 3, 4). The game has no generic hand-task type and does not need one. A hand task is an action in src/sim/90-actions that puts its duration on the object it touches (`device.maintenance.doneAt`, `workload.busyUntil`, `cluster.switching.doneAt`), bills remote hands when the object sits in a datacenter (pattern: `replaceComponent`, src/sim/90-actions/hardware.ts:417, `DataCenter.remoteHands` in src/sim/20-world/datacenters.ts:11), and has a matching technician operation so a hired technician can run it: a new `OpKind` in src/sim/47-staff/technicians.ts:13 with an `OP_TASK` entry (:19) and a branch in `perform` (:92). The player starts it from the inspector or console; `queueOperation` (src/sim/90-actions/staff.ts:129) hands it to a technician. Record new hand tasks in the gdd.md "Core loop" By hand table.
- Commits: message of at most 4 words, no description, no co-author lines, never mention an AI tool. Commit and push each green piece; main deploys to GitHub Pages.
- Verify each lane with `npm run typecheck`, `npm test` (redirect output to a file and search it for FAIL), `npm run build`, `npm run balance` (scripts/balance.ts: 20 seeds, STEADY and SOLO bots, prints bankrupt count, a per-year table and the level 2 to 6 median years; report steady and solo medians before and after, keep them within about half a year, no bankruptcies) and, for early-game changes, `npx tsx scripts/happiness.ts` for 2005. Vitest runs in a node environment (vite.config.ts), so UI is checked with the Playwright MCP against a Vite dev server on a free port (not 5173), light and dark. To change state in the page, import the store through its exact module URL: `performance.getEntriesByType('resource').map(e => e.name).filter(n => n.includes('/src/ui/store.ts')).pop()`; the HMR query string matters, a plain import gives a second store. Dock apps open by dispatching a click on the `.tip` element's parent. Save screenshots to .impeccable/review/<lane>-*.png.
- The owner plays on the Vite dev server (port 5173) from this checkout, so merging code here reloads their page; windows and the Support selection survive reloads (src/ui/session.ts).
- One lane at a time on its own branch or worktree, merged into main only when everything above is green.

Balance today (main after Merge Lane 6.5): steady medians L2 2006.3, L3 2007.1, L4 2008.8, L5 2012.1, L6 2018.2; solo L2 2005.8, L3 2006.5, L4 2008.3, L5 2012.9, L6 never; 0 of 20 bankrupt in both. 865 tests pass.

### Lane 2.0: Alerts that pause the game

Owner's words: "There should be notification that pause and are a popup like bankruptcy warning."

State on main: notifications are banners (`Banner { id, app, title, text, hour }`, src/ui/store.ts:19, pushed at :264, at most 4 on screen, 50 in history) and never pause. Two things pause today: bankruptcy (`s.gameOver` set in src/sim/46-finance/finance.ts:110 with `event.bankrupt`; the store sets speed 0 at src/ui/store.ts:199 and Desktop renders src/ui/desktop/GameOver.tsx) and the four PHP advisory stages (`ADVISORY_KEYS` in src/sim/60-infra/security.ts:23; the store's advance loop at store.ts:190-199 sets `advisory: true` and speed 0 when such an event arrives; src/ui/desktop/SecurityAlert.tsx is the sheet, closed by its button or Escape). Cash below zero only emits `event.cashNegative` (finance.ts:108) as a banner with a sound (src/ui/sounds.ts:17). gdd.md "Open questions" still says nothing auto-pauses; the owner has changed that.

Decisions:
- One mechanism: `ALERT_KEYS` in a new src/sim/alerts.ts maps event keys to the app that handles them. When the advance loop sees an event with such a key, it stops advancing, sets speed 0 and sets `alert: Banner` in the store (replace the boolean `advisory` with `alert: Banner | null`; the SecurityAlert sheet becomes the body shown when the key starts with `event.vuln.`, every other key shows a plain alert body). The sheet: an icon, the event's title and text (the existing i18n keys), up to two rows of labels and values the key's body chooses, a primary button "Open <app>" (opens the app with a focus target where one exists) and "Continue" (resumes the speed from before the pause). Escape is Continue. The banner still goes into the notification history.
- Keys that pause, today's set: `event.cashNegative`, `event.loanMissed`, `event.loanCalled`, `event.vuln.announced`, `.poc`, `.warning`, `.patch`, `event.vuln.hacked`, `event.dataLoss`, `event.seized` (the legal server seizure, src/sim/60-infra/incidents.ts:140), `event.ddos` (attack start, src/sim/60-infra/network.ts:278), `event.gridDark` (a location without power, incidents.ts:86). `event.bankrupt` keeps the GameOver sheet. Later lanes add theirs: 2b.1 `event.vulnOpen` for a critical vulnerability on own software, 2b.4 the extortion ticket, 3.4 `event.dataCorrupted` after a pulled plug. Everything else stays a banner.
- No setting to turn them off (the owner asked for them); the Sound setting keeps covering the chime.
- Update gdd.md "Open questions": "Which events auto-pause the game?" now reads: alerts, listed in "The desktop".

Target: alerts.ts, the store change, the generic sheet with the security body kept, the key list, GameOver untouched. Tests: tests/alerts.test.ts for the pure part (`isAlert(key)`, the app per key) and tests/ui-store.test.ts for the pause (advance stops at an alert event and sets speed 0, Continue restores it). Verify typecheck, tests, build. Playwright: let cash go negative and see the sheet pause the clock, Continue resumes, light and dark, screenshots. Record in gdd.md "The desktop" ("Alerts" paragraph with the list) and fix the open question.

### Lane 2.0b: News feed and notification settings per type

Owner's words: "Oh new unlocks should be in the news maybe, and the news should be side notifications maybe, also notifications add a settings wheel and they should be able to customize their notifications!" And: "also as in the types of notifications they get per app".

State on main: notifications are banners from the store's `notify(app, title, text, key?)` (src/ui/store.ts:73, pushed at :264), at most 4 on screen at the right, 50 kept in the notification centre (`history`, opened from the bell in src/ui/desktop/MenuBar.tsx:69, `unseen` badge). Preferences are per app only: `NotifyPref { allow, sound }` (store.ts:21), `prefOf` (:29), `setNotifyPref` (:246), stored in localStorage under `backbone.prefs` (:32), edited in Settings (src/ui/apps/SettingsApp.tsx:51, one row per app). Every event carries `app` and `key` (`SimEvent`); the key names its kind (`event.vuln.hacked`, `event.review`, `event.ddos`, `event.saturated`, `event.networkBills`, `event.tax`, `event.cashNegative`, and so on; `rg -o 'key: "event\.[a-zA-Z.]+' src/sim | sort -u` lists them all). Alerts (Lane 2.0) always show. Nothing in the game announces that new software, hardware or options have become available: software has `from` years (platforms.ts), server generations arrive every three years (economy.ts GENERATIONS), IPv6 arrives in 2010 and 2013 (addresses catalog), design generations every four years (Lane 2.1), registrar and email providers from their years (Lane 2.1b), hardware leaves the shop (Lane 5.1). The AlertSheet names punned outlets ("Heize online", "Twister", ...) in `SOURCE` (src/ui/desktop/AlertSheet.tsx:10).

Decisions:
- Notification types. A type is a group of event keys inside an app. `NOTIFY_TYPES` in a new src/ui/notify-types.ts: `Record<app, { id: string; label: string; match: (key: string) => boolean }[]>`, plus a fallback type "Other" per app for keys no group claims. Groups per app, as labels the player understands (the i18n keys stay internal): Finance: Bills and tax, Cash and loans; Support: Tickets, Notices and legal; Network: Uplinks and peering, Attacks and saturation, Addresses, Monthly bills; Locations: Hardware failures, Power, Deliveries and moves; Security: Advisories, Compromises; Marketing: Reviews, Campaigns and bills; Website: Site; Staff: Hiring and leaving, Training; Virtual machines: Workloads and migrations, Backups; Customers and Billing: Orders, Payments and dunning; Research: Unlocks; News: Hardware, Software, Internet, Market. Write the mapping by reading the key list; a test asserts every key the sim can emit lands in exactly one group of its app (reuse the key collection in tests/event-keys.test.ts).
- Preferences gain `types: Record<string, boolean>` (missing means on): `NotifyPref { allow, sound, types }`. A notification shows when the app allows and its type is on; alert keys ignore both (they always pause and show). Sound follows the app as today. Old prefs load with every type on.
- Settings wheel: a gear button in the notification centre header (next to Clear) opens Settings on the Notifications section, with the app's row expanded; each app row in Settings expands to its types with an On/Off segmented control per type (no dropdowns, no helper text). Keep the per-app Notifications and Sound switches.
- News. A sim module src/sim/80-business/news.ts emits `event.news.<topic>` events from the app "News" on the day a thing becomes available: a software's `from` year (one per software, at 1 January 09:00 with the punned product name), a new server generation and its first shop day, NVMe bays (G4) and other chassis changes if Lane 4 recorded a year, IPv6 at datacenters (2010) and on home lines (2013), RIPE's last /8 (September 2012) and run-out (November 2019), a new website design generation (every four years from 2009), new registrar or email providers from their years (Lane 2.1b, when built), a product line the player could offer now but does not (checked monthly, once per line), and later lanes add theirs (end of sale, GPU demand waves, part price spikes) by pushing to `NEWS` with a year or hour and a key. Each key has `.title` and `.text` written as a dry headline and one sentence, attributed to a punned outlet picked by topic (reuse and extend `SOURCE`: "Heize online" for hardware and software, "Golem.dy" for internet, "Handelsblah" for market). The headline is the title, the outlet is part of the text.
- News are side notifications: they go through `notify("News", ...)` like every other event, so the banner stack shows them and the News types in Settings can mute them. They also fill a News app: a dock app (hidden by default like Notes is, opened from the bell's menu and from Searchlight later) listing headlines by date, newest first, with the outlet and the sentence; labels and values. Window 520 by 640.
- Old saves: news for things that happened before the save's current date are not replayed; `s.news: string[]` records emitted keys so nothing repeats (default [] in newGame and deserialize).

Target: notify-types.ts and the test over every key; `types` on prefs with load and save; the gear and the expanded Settings rows; news.ts with the sources above, `event.news.*` i18n in a new src/i18n/news.ts spread into en.ts; the News app and registry entry; `s.news`. Tests: tests/notify-types.test.ts (every key in one group; a key of an off type is hidden; alert keys are not), tests/news.test.ts (software news on its first year, generation news, IPv6 news dates, a line offerable but not listed produces one news item, nothing repeats, old saves load). Verify typecheck, tests, build (no money moves, balance untouched). Playwright: the gear in the notification centre, switch a type off and see its banner stay away, the News app with the 2008 generation headline, light and dark, screenshots. #### Lane 2b.1: Software versions, generated vulnerabilities, monitoring, updating own software

Decisions:

- Generated vulnerabilities: a pure function `vulnsFor(familyId, year, seed)` in a new src/sim/60-infra/vulns.ts returns that year's vulnerabilities for a software family, seeded by (family, year) so every save sees the same ones. #### Lane 2b.4: Breaches, ransom and fines

Decisions:
- A critical vulnerability exploited on an own instance (panel, hypervisor, game panel) that has been exposed more than 30 days becomes a breach with 25% chance instead of a plain compromise: customer data on that host is stolen. New ticket kind "extortion" (also used by the i18n as a legal notice) with actions `pay` and `refuse`, due in 72 hours; no decision by then counts as refuse. Its text says the data is offered for sale online and names the sum. Creating it emits `event.breach`, which is an alert (Lane 2.0): the game pauses and the sheet's primary button opens the ticket in Support. Ransom demand: 2 × the monthly revenue of the customers on that host, minimum EUR 500, maximum EUR 50,000; from 2013 × 3, from 2020 × 5 (anchors: Symantec's average 2016 ransom USD 679, small-business ransoms USD 500 to 50,000 in 2016, NetDiligence SME median demand USD 12,000 in 2017 to 2020, Coalition's USD 1.2 million average in 2021 for insured firms).
- Paying: 90% the data is not sold (nothing further happens except the money and a `notice` style ledger line `ledger.ransom`); 10% it is sold anyway. Refusing: sold. When sold: every customer on the host loses 40 happiness, 30% of them churn at once, 20% leave a 1-star review (reason "dataLoss"), awareness in every city drops 20% (`addAwareness` negative), and a data protection fine follows after 30 days with the chance and size below. Press coverage is a notification `event.breachPress`.
- Fine: before 25 May 2018 (the old BDSG, up to EUR 300,000 by law and rarely used): 20% chance, EUR 2,000 to 25,000 drawn log-uniform. From 25 May 2018 (GDPR, up to 2% or 4% of turnover; anchor the 1&1 fine of EUR 9.55 million in 2019 for a large company): 50% chance, 2% of the last twelve months' revenue, minimum EUR 2,000, maximum EUR 200,000. Booked under `ledger.fine`, category "fees" (or the nearest existing expense category; record it).
- The Security app gets a Breaches card listing past breaches with date, host, decision and outcome. Labels and values.

Target: breach branch in the exploitation roll, extortion ticket with actions and the 72-hour default, outcomes, fine timer, Security card.
